## 問題 1：`--oos-start` 偷偷凍結了訓練集

### 症狀

```
不指定 oos_start        訓練 138 → 150 → 162 → 174 ... 294   擴張
只給 oos_start          訓練 168 → 168 → 168 → 168 ... 168   凍結
oos_start + dev_end     訓練 168 → 168 → 168 → 168 ... 168   凍結
```

後兩行完全相同 ⇒ `--dev-end` 變成死參數。

### 為什麼會這樣

修正前的程式碼把隔離量從迴圈裡拿掉了：

```python
# 修正前
train_end = training_limit if training_limit is not None else cursor - gap
#           ^^^^^^^^^^^^^^ 迴圈外算一次，之後永遠不變
```

程式碼裡的理由是：

> 凍結點前最後 gap 期的標籤要用到 OOS 價格才能揭曉，因此不只第一個
> fold 要剔除；後續所有 fold 都必須永久維持同一截止點。

**前半對，後半不成立。**

```
fold 1   測試 d[180:192]   訓練到 d[167]   d[168..179] 的標籤還沒揭曉 ✓ 要剔除
fold 2   測試 d[192:204]   訓練到 d[179]   d[179] 的標籤在 d[191] 揭曉
                                          d[191] < d[192]，早就揭曉了 ✓ 可用
```

「前一個 fold 的測試資料在後續 fold 變成訓練資料」正是 walk-forward
的定義——實盤上每季重新校準就是這樣做的，不是洩漏。

CLAUDE.md 禁令 5 寫的也是「滾動訓練，只用預測期之前的資料」。

### 凍結不是錯的，是**另一個實驗**

| 模式 | 回答的問題 |
|---|---|
| 擴張 | 照這個方法持續運作，OOS 期間表現如何 |
| 凍結 | 模型不更新的話，多久會衰退 |

兩個都有價值。但凍結 2.7 年代表校準器越來越舊，**跑出來表現差就分不清
是「訊號無效」還是「模型過期」**。這正好是要回答的問題，不能混在一起。

### 修法：讓 API 形狀對上語意

```python
# 修正後：隔離永遠在迴圈裡，牆只是額外上限
while cursor + test_span <= len(dates):
    train_end = cursor - gap                          # 逐 fold 擴張
    if training_limit is not None:
        train_end = min(train_end, training_limit)    # dev_end 才是牆
```

```
--oos-start   OOS 從哪一天開始（只切分）
--dev-end     訓練硬牆（要凍結就明講）
```

修正後三種模式各自不同：

```
不指定 oos_start        138 → 150 → 162 → 174 ... 294
只給 oos_start          168 → 180 → 192 → 204 ... 288   從凍結點起擴張
oos_start + dev_end     168 → 180 → 180 → 180 ... 180   撞牆停住
```

第二列的 `168 → 180` 為什麼跳 12？因為隔離永遠是 12 期：
fold 1 訓練到 `180-12`，fold 2 訓練到 `192-12`。

### 順帶：Codex 抓到的漏洞是真的

修正前的前一版是：

```python
training_limit = cursor          # dev_end is None 時
...
train_end = min(cursor - gap, training_limit)
```

fold 2 以後 `cursor - gap` 會大於 `cursor_初始`，`min` 選中後者
⇒ **完全沒套隔離**。Codex 該修，只是修錯方向。

現在的寫法兩邊都守住：隔離無條件留在迴圈裡，牆當額外上限。

## 問題 2：帳本沒存 `edge_z`（禁令 8）

### 症狀

`--edge-z` 是 CLI 可調、而且會改變選股結果的參數，卻沒進表。

唯一鍵是 `(data_asof, strategy_version, family, horizon, stock_id)`，
同一天掃兩組門檻、選到同一檔 ⇒ 第二筆被 `INSERT OR IGNORE` **靜默丟掉**。

帳本會長成「同一版本同一天，參數不明」。

### 為什麼這比看起來嚴重

前推帳本是**唯一會隨時間收斂**的證據來源：

```
1 年 →  4 個乾淨樣本   能偵測 Sharpe > 2.0
4 年 → 17 個乾淨樣本   能偵測 Sharpe > 1.0
6 年 → 25 個乾淨樣本   能偵測 Sharpe > 0.82
```

要等 4~6 年。四年後才發現「這些紀錄的參數不明」，等於四年白等。

禁令 8 就是為了這件事寫的。

### 修法：`edge_z` 進**主鍵與唯一鍵兩邊**

```sql
PRIMARY KEY (predicted_at, edge_z, family, horizon, stock_id),
UNIQUE (data_asof, strategy_version, edge_z, family, horizon, stock_id)
```

⚠️ 只加進 UNIQUE 不夠。這是實測抓到的：

```
edge_z=0.3 寫入 1 筆
edge_z=0.8 寫入 0 筆   ← 撞上 PRIMARY KEY
```

**同一次執行**掃兩組門檻時 `predicted_at` 相同，第二筆會撞主鍵。
靠時間戳差異避開碰撞是假的保護。

單元測試原本用不同 `predicted_at` 建兩筆，剛好避開了這個洞——
測試通過但保護不存在。改成兩筆共用同一個 `predicted_at` 才守得住。

## 問題 3：`pd.offsets.BDay` 不懂台股休市

### 症狀

```python
due_date = (pd.Timestamp(as_of) + pd.offsets.BDay(horizon)).date()   # ← bug
```

`BDay` 只跳週末。實測 2015-2026 的 2,850 個交易日：

| 交易日數 | 實際中位跨度 | BDay 推算 | 誤差 |
|---|---|---|---|
| 20 | 29 日 | 28 日 | −1 |
| 60 | **89 日** | **84 日** | **−5** |
| 120 | 180 日 | 168 日 | −12 |

單次最糟差 14 天：

```
進場 2025-01-02，持有 60 個交易日
  實際揭曉日   2025-04-10
  BDay 推算    2025-03-27      ← 中間卡了農曆年與 228
```

### 影響範圍（為什麼列在第 3 而不是第 1）

結算守門用的是實際列數：

```python
if len(bars) - decision_idx - 1 < item.horizon:
    continue
```

所以**不會誤結算**。壞掉的只有印給使用者的「預計揭曉」——早兩週。

但這仍是禁令 11 同一條原則的延伸：**日期一律用實際發生的那天，
不用推算出來的那天。**

### 修法：能查就查，不能查才推估

前推預測的揭曉日在**未來**，資料庫裡還沒有那些交易日，所以一定要推估。
關鍵是推估方式：

```python
future = calendar[bisect_right(calendar, as_of):]
if len(future) >= horizon:
    return future[horizon - 1]          # 查得到就直接數
return as_of + timedelta(days=median_calendar_span(calendar, horizon))
```

推估用**歷史上同樣交易日數的實際跨度中位數**。中位數比平均數穩健：
農曆年那幾週會把平均往上拉，但它一年只出現一次。

錨點是 `as_of`，**不是日曆末端**——否則補記舊預測會全部擠在同一天。

### 同一個 bug 的第二個出口

```python
train_end = pd.Timestamp(as_of) - pd.Timedelta(days=horizon * 2)   # ← 魔術數
```

`horizon * 2` 日曆日是個湊出來的保守值（120 日曆日 ≈ 85 交易日 > 60），
碰巧夠用，但跟 `walk_forward.embargo_periods` 的定義對不上，而且會隨
農曆年漂移。改成直接數交易日曆：

```python
as_of_index = bisect_right(calendar, as_of) - 1
train_end = pd.Timestamp(calendar[as_of_index - horizon])
```

## 問題 4：重複索引

```
sqlite_autoindex_forward_predictions_1     ← PRIMARY KEY 自動建
sqlite_autoindex_forward_predictions_2     ← UNIQUE 約束自動建
ux_forward_prediction_identity             ← 手動建，欄位與上一個完全相同
```

SQLite 的 table-level `UNIQUE(...)` 本來就會建索引。再手動
`CREATE UNIQUE INDEX` 在同一組欄位上，只是雙倍儲存與雙倍寫入成本。

刪掉手動那個，並加測試守住：

```python
assert all(name.startswith("sqlite_autoindex_") for name in names)
assert len(names) == 2
```

## 順帶補的防線

### 舊結構要拋錯，不可靜默沿用

`CREATE TABLE IF NOT EXISTS` 對既有表是**無聲的**。舊帳本缺 `edge_z`
時會安靜地繼續用舊結構，然後寫入失敗或欄位錯位。

```python
missing = [name for name in _COLUMNS if name not in existing]
if missing:
    raise ForwardStoreError(f"... 缺少欄位 {missing}；這是舊版結構，請先備份後重建該表")
```

### 欄位清單由 dataclass 推導

原本 INSERT / SELECT 各手寫一份欄位清單，加一個欄位要改三個地方。
改成從 `dataclasses.fields()` 推導，少一個 DRY 破口。

## 這四個問題的共同教訓

```
它們都不會拋錯。
四個都只是讓數字悄悄偏掉。
```

- 訓練凍結 → 表現差，但分不清原因
- 參數沒存 → 四年後才發現證據不完整
- `BDay` → 日期早兩週，沒人會注意
- 重複索引 → 只是慢，永遠不會有人查

**測試要守的是「性質」，不是「目前的輸出」。** 問題 2 的單元測試原本
就通過了——因為它用不同的 `predicted_at` 建兩筆，剛好避開真正的碰撞。
測試通過但保護不存在。
