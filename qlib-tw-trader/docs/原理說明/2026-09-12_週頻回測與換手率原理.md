# 週頻回測與換手率原理

- 日期：2026-09-12
- 程式：`taiwan-quant/taiwan_quant/backtest/engine.py`
- 測試：`taiwan-quant/tests/test_backtest.py`（28 個測試）

---

## 為什麼是週頻

使用者的需求是「未來 **5 個交易日**的投資建議」。

5 個交易日 = 一週。這是**週頻**問題，不是日頻也不是 tick 頻。

ChatGPT 來源在五輪對話後也收斂到同一結論（見 `docs/需求規劃/202609/來源原文/02_ChatGPT`）：

> 每週固定產生下一週的投資計畫：哪一檔、什麼價格區間買、什麼價格賣、風險失效點。
> 即時資料仍然要，但它是用來**修正**「下週計畫」，不是讓系統每天重新選股。

週頻的三個好處：

1. **回測乾淨**：每週 3 個計畫，長期執行的績效可以直接統計
2. **換手率可控**：日度調倉在台股成本結構下不可執行（見下節）
3. **MVP 小很多**：不需要盤中資料、不需要即時串流

## 引擎的職責邊界

```
labeling/    決定進出場與毛報酬        （triple-barrier）
ranking/     決定每週挑哪幾檔          （Top 3 + 投組約束）
backtest/    把計畫彙總成績效、扣成本、算換手率
```

回測層吃的是**已實現的交易計畫**（`TradePlan`），不做選股也不做標記。

**這個切分讓回測層不可能偷看未來**——它只看得到已經發生的結果，連原始價格資料都拿不到。

```python
@dataclass(frozen=True)
class TradePlan:
    week_id: str          # 決策週
    stock_id: str
    gross_return: float   # 毛報酬（由 labeling 算出）
    holding_days: int     # 實際持有交易日數
    tier: Tier            # 流動性分層（決定滑價）
```

## 規格 13：換手率是一級輸出

### 為什麼要提到「一級」

qlib-tw-trader 的問題不是「沒算換手率」，而是**只在離線腳本算、產品化路徑完全沒有**：

```
scripts/evaluate_models.py       有成本、有換手率（README 的數字來自這裡）
src/services/walk_forward_backtester.py   兩者都沒有（Dashboard 顯示這個）
```

結果：日度調倉的 **271.5% 週換手率**長期無人察覺。

所以本引擎的 `BacktestResult` 一定帶這兩個欄位，**即使呼叫端用毛報酬模型也會算出來**：

```python
weekly_turnover: float      # 平均週換手率（單邊）
annual_cost_drag: float     # 由換手率推算的年化成本拖累
```

測試 `test_turnover_is_always_reported` 把這條釘住。

### 換手率怎麼算

```
每週換手率 = 一週交易日數 / 平均持有交易日數
           = 5 / avg_holding_days
```

| 平均持有 | 週換手率 | 意義 |
|---|---|---|
| 1 天 | 500% | 每週換五輪 |
| 5 天 | 100% | 每週剛好換一輪 |
| 10 天 | 50% | 每週換半輪 |
| 25 天 | 20% | 每五週換一輪 |

**這條公式把「持有期」與「成本」直接綁在一起**，讓「持有期是成本的主導因素」在程式裡看得見，而不是藏在註解裡。

### 年化成本拖累

```
年化來回次數 = 週換手率 × 52
年化成本拖累 = 年化來回次數 × 一趟來回成本率
```

實測對照（0050 分層、6 折、含 0.3% 滑價 → 來回 1.071%）：

| 週換手率 | 年化來回 | 年化拖累 | 情境 |
|---|---|---|---|
| 9.9% | 5.15 | **5.51%** | qlib-tw-trader 的 HoldDrop 策略 |
| 100% | 52.0 | 55.69% | 平均持有 5 天 |
| **271.5%** | 141.2 | **151.2%** | qlib-tw-trader API 的日度調倉（實測） |

最後一列是決定性的：**年化成本 151% 代表任何毛報酬都會被吃光。** 日度調倉在台股不可執行。

## 規格 15：成本敏感度必須並列

```python
def run_cost_sensitivity(plans, scenarios=None) -> dict[str, BacktestResult]:
    """一次跑完所有成本情境"""
```

預設四個情境：

```
無成本（毛報酬）
僅手續費+證交稅（無滑價）      ← qlib-tw-trader 的模型
6折+滑價（預設）
無折扣+滑價
```

### 為什麼強制並列

實測（20 週、同一組交易）：

```
無成本             +26.27%
僅手續費+證交稅      +0.41%
含滑價             −19.08%
```

**只報一個數字，讀者無法判斷結論有多脆弱。**

若某策略只在「無滑價」假設下賺錢，那個結論就不該被採信——而不並列的話，讀者根本看不出來。

### 換手率在所有情境必須相同

```python
def test_sensitivity_all_share_same_turnover():
    turnovers = {r.weekly_turnover for r in results.values()}
    assert len(turnovers) == 1
```

換手率是**策略屬性**，與成本模型無關。若不同，就代表換手率計算被成本模型汙染了——這是一個會靜默產生錯誤結論的 bug。

## 週內多部位：等權平均，不是相加

```python
gross = statistics.fmean(p.gross_return for p in batch)
```

同一週三檔各 +10% → 該週 **+10%**，不是 +30%。

這對應「把資金分成三份、各買一檔」。相加等於假設每檔都用滿資金（3 倍槓桿）。

測試 `test_positions_within_week_are_equal_weighted`：兩檔 +10% 與 0% → 該週 +5%。

## 複合順序必須正確

```python
ordered = sorted(plans, key=lambda p: p.week_id)
```

複合是**有序運算**：

```
+50% 然後 −50%  →  1.5 × 0.5 = 0.75   （虧 25%）
−50% 然後 +50%  →  0.5 × 1.5 = 0.75   （同樣虧 25%）
```

這個例子剛好相同，但最大回撤完全不同：

```
+50% → −50%：權益 1.0 → 1.5 → 0.75，最大回撤 50%
−50% → +50%：權益 1.0 → 0.5 → 0.75，最大回撤 50%
```

順序影響回撤路徑與 Sharpe 的時序意義。輸入亂序不可影響結果。

測試 `test_weeks_sorted_even_if_input_unordered`。

## 指標的邊界處理

### Sharpe 回 None 而非 0

```python
if len(returns) < 2:
    return None          # 單一樣本無法算標準差
if sd == 0:
    return None          # 零變異，Sharpe 無定義
```

**不可回 0 或 inf。** 回 0 會讓下游誤以為「算出來了，結果很差」，而實際是「無法計算」。

這與柵欄寬度那個 NaN bug 是同一類設計原則：**無法計算時要明確表示，不可用一個看起來像答案的數字掩蓋。**

### 最大回撤

```python
equity = 1.0; peak = 1.0; worst = 0.0
for r in returns:
    equity *= 1.0 + r
    peak = max(peak, equity)
    worst = max(worst, (peak - equity) / peak)
```

用**權益曲線的峰谷差**，不是報酬序列的最小值。

手算驗證（測試 `test_max_drawdown_on_known_path`）：

```
週報酬 +10%, −20%, +5%
權益   1.0 → 1.10 → 0.88 → 0.924
高點 1.10，谷底 0.88
最大回撤 = (1.10 − 0.88) / 1.10 = 20%
```

### 年化

```python
growth = 1.0 + cumulative
if growth <= 0:
    return -1.0          # 全部虧光，年化 −100%
return growth ** (52 / weeks) - 1.0
```

`growth <= 0` 的保護是必要的——負數開分數次方在浮點運算會產生 NaN 或複數。

## 輸入驗證

### NaN 報酬必須在邊界擋掉

```python
if not math.isfinite(self.gross_return):
    raise ValueError(
        f"gross_return 必須為有限值，得到 {self.gross_return}。"
        "NaN 會汙染整個複合結果且不會拋錯——必須在邊界擋掉。"
    )
```

一個 NaN 報酬進到 `_compound()`：

```python
acc *= 1.0 + float('nan')    # acc 變成 NaN，且不會拋錯
```

**整個回測結果變成 NaN，而且沒有任何錯誤訊息。** 這與柵欄寬度的 NaN bug 是同一個教訓的不同面向。

### 空清單必須報錯

```python
if not plans:
    raise ValueError("交易計畫清單不可為空")
```

回一個「零交易的結果」會讓下游誤以為「跑過了，只是沒有訊號」。
