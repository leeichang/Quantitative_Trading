## 系統定位：只推播，不下單

使用者的原始需求：

> 傳送訊息到 telegram 給使用者就可以！**不用直接下單**

**7/7 個 AI 來源一致同意這條。** 這是整個系統最沒有爭議的設計決定。

理由：

| 面向 | 不下單的好處 |
|---|---|
| 安全 | 不需要券商 API 金鑰，沒有誤單風險 |
| 法遵 | 不涉及代客操作 |
| 工程 | MVP 範圍小很多，不需要處理委託狀態機、部位同步、斷線重連 |
| 責任 | 最終決策在人，系統只提供研究素材 |

程式層面有測試把關：

```python
def test_message_never_contains_order_instructions():
    """訊息不可含任何下單指令字樣"""
    for forbidden in ("立即下單", "馬上買進", "掛單", "委託"):
        assert forbidden not in message
```

措辭上也不暗示執行。

## 三條硬規定

### 1. Token 走環境變數，程式碼中無明文

```python
@classmethod
def from_env(cls) -> TelegramConfig:
    return cls(
        bot_token=os.environ.get("TELEGRAM_BOT_TOKEN", "").strip(),
        chat_id=os.environ.get("TELEGRAM_CHAT_ID", "").strip(),
    )
```

三層防護：

**（a）擋掉佔位字串**

```python
PLACEHOLDER_VALUES = frozenset({
    "", "your_token_here", "YOUR_TELEGRAM_BOT_TOKEN", "YOUR_CHAT_ID", "xxx",
})
```

不擋的話，使用者複製 `.env.example` 後會以為設定好了，實際推播到不存在的 bot——**而且不會有錯誤**（Telegram API 會回 401，但使用者看不到）。

**（b）`__repr__` 遮蔽 token**

```python
def __repr__(self) -> str:
    masked = "***" if self.bot_token else "(未設定)"
    return f"TelegramConfig(bot_token={masked}, chat_id={self.chat_id!r})"
```

例外訊息、traceback、除錯輸出都可能外洩。

**（c）例外訊息不串接原始錯誤**

```python
except httpx.HTTPError as exc:
    # 不可把 exc 直接串進訊息——httpx 的錯誤會含完整 URL（內含 token）
    raise TelegramError(
        f"推播失敗：{type(exc).__name__}。..."
    ) from None
```

`httpx` 的錯誤訊息帶完整 URL，而 Telegram 的 token 就在 URL 路徑裡：

```
https://api.telegram.org/bot{TOKEN}/sendMessage
```

用 `from None` 切斷 `__cause__`，避免 traceback 印出原始例外。

測試 `test_error_message_does_not_leak_token` 驗證這條。

### 2. `--dry-run` 完全不發網路請求

```python
def test_dry_run_does_not_send(monkeypatch):
    def explode(*args, **kwargs):
        raise AssertionError("dry-run 不應發出任何 HTTP 請求")
    monkeypatch.setattr(httpx, "post", explode)
    ...
```

測試直接把 `httpx.post` 換成會爆炸的函式。若實作不小心發了請求，測試立刻失敗。

**為什麼這麼嚴格**：開發時誤發訊息到真實頻道是不可逆的。

### 3. 推播失敗必須拋錯，不可靜默吞掉

```python
raise TelegramError(f"推播失敗：{type(exc).__name__}...")
```

**使用者以為收到建議、實際沒發出去，比明確報錯危險得多。**

但未設定 token 時是**優雅降級**（印出而非拋錯）——使用者可能只想看看訊息長怎樣。

兩者的區別：

| 情境 | 行為 | 理由 |
|---|---|---|
| 未設定 token | 印出，回 True | 使用者沒打算發，只是想看 |
| 設定了但發送失敗 | **拋錯** | 使用者預期發出去了，必須知道沒成功 |

## 訊息長度分段

Telegram 單則訊息上限 **4096 字元**。超長會被 API 拒絕，**整份建議都發不出去**。

```python
def _split_message(message: str, limit: int = MAX_MESSAGE_LENGTH) -> list[str]:
    """盡量在換行處切，避免把一筆交易計畫從中間斷開"""
```

在換行處切而非硬切，讓每一段都是完整的行。單行就超長（極少見）才硬切。

### 為什麼對照組要放進推播

Kimi 的意見（見 `來源原文/06_Kimi`）：

> 若三策略近五年都跑輸買進持有（台積電這類強趨勢股常見），
> 就代表短打策略沒有優勢

**看不到對照組就無法做這個判斷。** 只看到「本策略 CAGR 14.2%」會覺得不錯，並列「買進持有 21.5%」才知道其實跑輸。

### 為什麼版本號要放進推播

沒有版本號就無法回答：

> 為什麼 2026-09-12 系統推薦這支股票？當時用的是哪版模型？哪組參數？

CLAUDE.md 禁令 7、8 要求可稽核。推播訊息是使用者唯一會保存的記錄。

### 為什麼警告要放進推播

```python
def test_message_surfaces_warnings():
    """投組警告（例如沒有 defensive）必須出現在推播裡，不可只留在 log。"""
```

使用者不會看 log。投組集中在高 beta 這種風險，必須出現在他唯一會讀的地方。

### 「本週沒有標的」也要推播

```python
def test_message_when_no_positions():
    """
    「這週沒有值得買的」是合法且重要的結論，必須明確推播。
    靜默不發會讓使用者以為系統壞了。
    """
```

這是週頻系統的常態，不是異常。

## 端到端管線

```
標的池解析（真實快照 or 市值代理）
    ↓
日 K 載入（還原股價、剔除資料洞）
    ↓
技術特徵（16 個，通過物理截斷掃描）
    ↓
規則式分數（momentum baseline）
    ↓
機率校準（只用訓練期資料）       ← 關鍵環節
    ↓
柵欄推導（ATR + 報酬分位數）
    ↓
Triple-barrier 標記
    ↓
Top 3 選股（動態門檻 + 投組約束）
    ↓
部位規模（零股，兩道上限取小）
    ↓
Telegram 推播（dry-run 預設）
```

### 為什麼第一版刻意不用 ML

```
1. 完全透明，任何異常一眼看得出來
2. 沒有訓練，不可能過擬合
3. 提供 ML 模型必須超越的地板——跑不贏這個就不必談複雜模型
```

CLAUDE.md：**先有 baseline 再談複雜度。**

qlib-tw-trader 的教訓：303 因子 + DoubleEnsemble + Optuna + 16 小時訓練，最後 live IC 是 −0.0263。複雜度不等於優勢。

### 這個結果證明了什麼

| ✓ 證明 | ✗ 不證明 |
|---|---|
| 整條管線接得起來 | 任何預測能力 |
| 各模組在真實資料上可運作 | 策略有優勢 |
| 校準確實擋下了未校準會通過的標的 | 可以拿去交易 |
| 「沒有標的」這個結論能正確產出 | — |
