# Block bootstrap：累積報酬的區間寬到讓每一個比較都分辨不出來

- 日期：2026-09-18
- 起點：`docs/交接手冊/03_待辦與改進方向.md` 第 3 項「有效樣本太少 → 用 block bootstrap 估信賴區間」
- 對應程式：`taiwan_quant/validation/bootstrap.py`（新增）、`scripts/diagnose_bootstrap_intervals.py`（新增）
- 報告：`reports/bootstrap_intervals_dev.json`、`reports/bootstrap_intervals_oos.json`
- 測試：938 passed（新增 37）

## 驗收條件的答案

待辦寫的驗收條件是：

> **怎麼判斷做成了**：能回答「+1076% 的 95% 信賴區間是多少」。
> 如果下界低於買進持有，結論就是「無法區分」。

**答案：下界不只低於買進持有，低到負值。而且每一個基準都落在區間裡面。**

樣本外那份已發佈的結果（16 期，H=40，N=10）：

```
動能突破 N=10 累積淨報酬        +138.83%
95% 區間（block=1）            [−13.34%, +587.23%]     寬 600 個百分點

報告自帶的七個基準，全部落在區間內：
  0050 買進持有                +242.15%   ✓ 區間內
  0051 買進持有                +110.22%   ✓ 區間內
  0056 買進持有                 +96.67%   ✓ 區間內
  等權全池                      +61.45%   ✓ 區間內
  隨機 10 檔中位                +58.82%   ✓ 區間內
  隨機 10 檔 5% 分位            +15.10%   ✓ 區間內
  隨機 10 檔 95% 分位          +120.97%   ✓ 區間內
```

**那份報告做過的每一個比較，都在它自己的信賴區間裡面。**

「超過隨機 95% 分位」「輸 0050」「贏等權全池」——三句話都是區間寬度的
產物，不是策略的性質。

### 每趟報酬也含零

```
每趟淨報酬         +6.582%
常態 95% 區間      [−0.949%, +14.113%]
bootstrap 95%     [−0.322%, +13.928%]    含零
```

**16 期的樣本外連「這個策略會賺錢」都沒有建立。**

## 這取代了今天早上的論證

今天早上我撤回「超過隨機 95% 分位」，理由是弱虛無換成嚴格虛無時，
加法與乘法兩種搬法給出相反判定，而真測違反禁令 6（見
`2026-09-18_超過隨機95分位這句話該退休.md`）。

**那個論證是對的但繞了遠路。** 直接的版本是：

```
策略自己的 95% 區間   [−13.34%, +587.23%]
弱虛無 95% 分位       +120.97%   落在區間內
嚴格虛無（任一搬法）    +133.61% 或 +153.95%   兩者都落在區間內
```

**門檻定在 121%、134% 還是 154% 都無所謂——三個數字都在區間裡。**
不需要爭論搬法，因為策略的不確定性本身就大於整個爭論的範圍。

而且區間 `[−13.34%, +587.23%]` 的寬度（600 pp）遠大於整個弱虛無分布的
全距（`+15.10%` 到 `+120.97%`，106 pp）。**策略估計的雜訊是虛無分布
散布的六倍。**

## 待辦第 3 項的診斷只對一半

待辦把原因寫成「有效樣本太少」：

```
60 日持有   有效獨立樣本 30 個
120 日持有  有效獨立樣本 15 個
```

**對水準序列是對的，對配對差異是錯的。** 實測 lag-1 自相關：

```
水準序列（開發集 36 期）        配對差異序列
等權全池        −0.281        模型 − 打亂        −0.023
隨機 10 檔      −0.277        模型 − 手工        +0.080
標籤打亂        −0.278        手工 − 打亂        −0.074
```

配對差異的自相關**幾乎是零**，所以有效樣本就是 36，沒有被相依性折損。
問題在別處——**超額峰度**：

```
序列                  超額峰度（常態 = 0）
LightGBM baseline          +4.71
隨機 10 檔                 +4.26
等權全池                   +4.28
標籤打亂                   +3.35
手工分數                   +1.91
```

**t 檢定假設常態，而 n=36 的中央極限定理對這種尾部收斂得很慢。**
失準的地方是區間的尾端，而尾端正是判定顯著與否的位置。

所以「有效樣本太少」要拆成兩句：

```
水準序列      有相依性（負自相關），但那降低長期變異，不是問題來源
配對差異      沒有相依性，問題是尾部形狀
```

---

## 一個重要的否定結果：t 檢定並沒有騙我

峰度 +1.9 ~ +4.7 聽起來很嚴重。但**五個配對比較的判定，t 與 bootstrap
完全一致**：

```
配對                     差異        t      bootstrap 95%        判定
模型 − 隨機             +3.127%   +3.22   [+1.291%, +5.147%]   顯著／不含零
打亂 − 隨機             −0.009%   −0.02   [−0.996%, +1.004%]   量不出／含零
模型 − 打亂             +3.136%   +2.82   [+1.020%, +5.461%]   顯著／不含零
模型 − 手工             +0.608%   +0.30   [−3.361%, +4.693%]   量不出／含零
手工 − 打亂             +2.528%   +1.38   [−0.756%, +6.166%]   量不出／含零
```

**先前所有基於配對 t 的結論都站得住。** 這包括：

- LightGBM 對正確虛無顯著（t = 2.82）
- LightGBM 與手工分數量不出差別（t = 0.30）
- 置換檢定行為正常（打亂 − 隨機 t = −0.02）

⚠️ 一個接近翻轉的格子：LightGBM 的**每趟**報酬，常態區間
`[−0.165%, +7.555%]` 含零，bootstrap `[+0.025%, +7.786%]` 不含零。
**下界 +0.025% 是刀鋒上的數字**，不足以宣稱任何東西。方向是 bootstrap
比 t 略寬鬆，與峰度的預期相反——這一格不要當結論用。

## 區塊長度的方向符合實測自相關

`block_length` 在 `validation/bootstrap.py` 裡是**必填參數**，沒有預設值。
因為它是一個要說明理由的選擇，而它的效果有方向性：

```
開發集（lag1 ≈ −0.28，負自相關）→ 區塊拉長會收窄區間
  LightGBM  block=1  [−16.5%, +1011.3%]
            block=2  [ −8.0%,  +873.6%]
            block=4  [ +1.2%,  +755.8%]

樣本外（lag1 = +0.248，正自相關）→ 區塊拉長會拓寬區間
  動能突破  block=1  [−13.3%,  +587.2%]
            block=2  [−23.8%,  +749.1%]
            block=4  [−16.2%,  +662.7%]
```

負自相關降低長期變異，正自相關提高它。**兩個方向都被實測證實**，
所以逐點 IID 重抽在這兩份資料上分別會高估與低估寬度。

`validation/external/__init__.py` 早先記過不引入外部
`timeseries.bootstrap_sharpe` 的理由：「逐點 IID 重抽，對自相關報酬會
低估區間寬度」。**那個判斷是對的，而現在有兩份實測支持它。**

⚠️ 樣本外只有 16 期，block=4 已經是序列的四分之一。那一欄的估計本身
就不穩（block=2 比 block=4 寬，非單調）。**16 期做區塊掃描已經接近
方法的下限。**

## 報告不存逐期序列，它的不確定性就永遠算不出來

這支腳本**只讀既有報告的 `per_period` / `series`，不重跑回測**。

那不是為了省時間，是因為禁令 6：樣本外區間已經用掉，重跑有動用它的
風險。**後處理沒有那個風險，所以可以隨時重跑。**

但這件事有前提——報告必須存了逐期序列。實際盤點：

```
存了逐期序列             lgbm_baseline_dev、constraint_cost_dev、
                        cost_floor_dev、task08_constraints_dev、
                        oos_momentum_top10_h40（per_period）
沒存                     hand_vs_uninformed_dev、limit_up_events_dev、
                        threshold_sweep_dev、delisting_policy_dev、
                        position_costs_dev、etf_rotation_dev
```

**待辦第 3 項點名的 `+1076%`（籌碼跟隨 × 60 日）算不出來**——沒有任何
報告保存了它的逐期序列，而重跑要動用已經用掉的區間。

```
□ 新規格：任何報告結論性數字的報告，必須保存逐期序列
```

否則那個數字的不確定性是**永久不可知**的，因為唯一的取得方式被禁令
擋住。這一條要進 CLAUDE.md。

## 對整體結論的影響

**配對比較不受影響，累積報酬的比較全部失效。**

```
仍然成立   模型對虛無顯著（配對 t = 2.82，bootstrap 一致）
           模型與手工量不出差別（t = 0.30，bootstrap 一致）
           置換檢定行為正常（t = −0.02，bootstrap 一致）
           成本結構的算術（不涉及抽樣）
           持有期下限的算術（不涉及抽樣）

失效       「樣本外 +138.83%」的任何比較——七個基準全在區間內
           「超過隨機 95% 分位」（今早已撤回，這裡是第二個獨立理由）
           「輸 0050 −103 pp」——0050 也在區間內
           「贏等權全池 +90 pp」——等權也在區間內
```

⚠️ **「輸 0050」失效的方向對策略有利，但那不代表策略更好。**
它代表那個比較做不出來。先前我把「輸 0050」當成最可靠的負面結論
（它出現在五份文件的加註裡），而它和正面結論一樣不可靠。

**兩個方向的結論要用同一把尺。**

## 為什麼配對能活下來而累積報酬不能

同一份 36 期資料，為什麼配對差異的區間夠窄而累積報酬的區間寬到無用？

```
配對差異   逐期相減消掉了市場共同變動，剩下的變異小得多
           模型 − 打亂 的 SE 是 1.11%，而模型本身每趟的 SE 是 1.97%
累積報酬   複利把每期的變異放大，16 或 36 次乘法之後尾部極長
           +6.58%/趟 的 ±1 SE 在 16 次複利後展開成數百個百分點
```

**這就是為什麼 CLAUDE.md 的必跑對照組是配對比較，而不是比累積報酬。**
那個規格選對了，只是先前的報告仍然在標題上寫累積報酬。

```
□ 建議：報告的結論句改用每趟配對差異，累積報酬降級為附錄
```

## 這個模組不做什麼

不回答「顯著嗎」。它回答「區間有多寬、含不含零」。

`excludes_zero` 是**描述**而不是判定——多重測試校正仍然要另外做
（`stats.deflated_sharpe_ratio`、`probability_of_backtest_overfitting`）。
一個 95% 區間在掃過 126 組參數之後不再是 95%。

---

## 測試怎麼確認不是空的

承重的測試是「區塊長度必須影響區間寬度」。構造一個每值重複 5 次的
序列，有效樣本是 n/5，所以平均數的 SE 應該是 IID 估計的 √5 倍。

**並且做了突變測試**：把實作改成忽略 `block_length`，確認測試會抓到。

```
突變（一律 IID）   4 failed, 23 passed
  test_block_length_equal_to_n_gives_a_circular_rotation
  test_blocks_are_contiguous_runs
  test_blocks_widen_the_interval_on_autocorrelated_data
  test_negative_autocorrelation_narrows_the_blocked_interval
還原              27 passed
```

2026-09-18 的持有期 off-by-one 是程式與測試照同一個誤解寫成，所以
測試驗證了我的理解而不是行為。**突變測試是對那件事的直接防範**——
它證明測試會因為實作變壞而失敗。

另外，腳本測試抓到一個真實缺陷：`BLOCK_SWEEP = (1, 2, 4)` 對 3 期的
序列非法，腳本會拋錯。已改成先篩過並把**篩掉哪些**記進報告
（`skipped_block_lengths`）——靜默少一欄就是靜默改變掃描範圍。
