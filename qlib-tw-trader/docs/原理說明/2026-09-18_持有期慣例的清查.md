## 一、六份實作，不是五份

```
taiwan_quant/models/lgbm_baseline.py:211            closes.shift(-horizon) / opens.shift(-1) - 1
scripts/diagnose_constraints.py:328                 closes.shift(-HOLDING_DAYS) / opens.shift(-1) - 1
scripts/diagnose_cost_floor.py:363                  closes.shift(-horizon) / opens.shift(-1) - 1
scripts/diagnose_position_costs.py:127              adjusted_closes.shift(-HOLDING_DAYS) / adjusted_opens.shift(-1) - 1.0
scripts/validate_hand_scores_vs_uninformed.py:190   closes.shift(-HOLDING_DAYS) / opens.shift(-1) - 1
scripts/validate_lgbm_baseline.py:205               closes.shift(-HOLDING_DAYS) / opens.shift(-1) - 1
```

第四行是我先前漏掉的。它用 `adjusted_opens`／`adjusted_closes`，
所以 `opens.shift(-1)` 這個字串搜不到它。

**搜字串會漏掉換過變數名的同一份邏輯。** 這正是「六份實作」本身的
問題在搜尋層面的複現——沒有單一來源，連清查都做不準。

### 最刺眼的一點

其中兩支腳本的註解**宣稱**有單一來源，程式碼卻自己算：

```
scripts/validate_lgbm_baseline.py:204            # data/integrity.holding_dates 都不一致。
scripts/validate_hand_scores_vs_uninformed.py:189  # data/integrity.holding_dates 都不一致。
```

這兩支**沒有 import 任何 integrity 函式**。

註解記錄了正確的意圖，程式碼沒有執行它。**註解不會被測試，
所以它可以永遠是對的而程式永遠是錯的。**

## 三、守門是死碼

```
assert_holding_price_completeness
  定義   taiwan_quant/data/integrity.py:128
  引用   tests/test_data_integrity.py:13, 76
  生產   零
```

Codex 在工作單 08 的任務 P 修的範圍缺陷（原本檢查整個候選池、把下市
當資料錯誤），修的是**生產環境沒人呼叫的函式**。

`validate_oos_momentum.py` 的守門來自 `select_holding_positions`，
那個函式在 `integrity.py:186-192` 獨立判斷，**從不呼叫 assert**：

```python
if settlement.kind is MissingPriceKind.MISSING_ENTRY:
    continue                                    # 買不到就跳過
if settlement.kind is MissingPriceKind.SUSPENDED_OR_MISSING:
    raise DataIntegrityError(...)               # 買到了卻結不了帳才是錯
```

這個設計是對的——正確的範圍是實際遞補者，不是整個候選池。
**但那代表 assert 版本已經被取代，只是沒被刪。**

### 為什麼這比沒有守門更危險

一個有測試、在公開介面上、名字叫 `assert_..._completeness` 的函式，
會讓人以為完整性有被守護。`tests/test_data_integrity.py` 會通過，
覆蓋率報告會算它有覆蓋。

**測試覆蓋率量的是「這行有沒有被執行過」，不是「產品有沒有用它」。**

## 方法上的教訓：`||` 分不出零匹配和命令壞了

清查過程中我兩次得到假陰性：

```bash
rg -n "shift(-1 -" --glob '*.py' || echo "  無殘留"
#                  ^^^^^^^^^^^^^ 本機 rg 經 rtk hook 解析到 BSD grep，
#                                --glob / -g / --type 全部 usage error
#                                                    ↑ fallback 因旗標錯誤觸發
```

印出「無殘留」兩次。實際有三處殘留（都是註解，但我當時不知道）。

**`||` 的退出碼語意是「前面失敗」，涵蓋「零匹配」和「命令根本沒跑」。**
在旗標未驗證的搜尋後面串一個宣告乾淨的 fallback，等於把工具錯誤
翻譯成好消息。

改用直接掃檔的 Python 腳本，沒有 routing 問題，而且能逐行印出上下文
——那才看見註解前面的 `#`。

## 共同的根因

六項發現裡有四項的直接原因相同：**沒有單一來源，所以連清查都不準確。**

```
forward 報酬六份實作      →  搜字串會漏掉換過變數名的那一份
integrity 覆蓋率          →  搜函式名會把註解算成呼叫
守門死碼                  →  兩個並存的守門，新的取代舊的但沒刪
stale 報告                →  兩代檔名並存，沒有機讀的取代關係
```

任務 V（統一 helper）不只是清潔工作。**它是讓後續清查可信的前提。**
