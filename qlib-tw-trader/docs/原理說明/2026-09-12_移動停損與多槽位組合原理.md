## 一、這份文件回答什麼

前一輪的結論是：**9 組 triple-barrier 策略全部輸給等權買進持有，差距 85 個百分點。**

機制解釋是「目標價把上檔封死」。路線 A 就是針對這個解釋動手：拿掉目標價，改成移動停損。

這份文件說明四件事：

1. 移動停損怎麼標記，為什麼那個判定順序不能顛倒
2. 停損幅度怎麼從資料推導（不可人工寫死）
3. 沒有目標價時，進場門檻與校準層怎麼改
4. 為什麼必須重寫回測引擎——以及那個改動翻轉了多少結論

## 二、移動停損標記

### 2.1 規則

```
初始停損 = 進場價 × (1 − trail_pct)
每日更新 = max(現有停損, 期間最高價 × (1 − trail_pct))   ← 只升不降
出場     = 盤中觸及停損線，或時間柵到期
```

上檔不封死 → 趨勢延續時一路跟上；回檔超過 `trail_pct` → 鎖住已實現獲利。

### 2.2 判定順序不可顛倒（最容易寫錯的地方）

每根 K 棒內，**必須先判定出場，才更新高點與停損**：

```python
# 正確
if bar_low <= stop:
    return exit(...)
if bar_high > peak:
    peak = bar_high
    stop = max(stop, peak * (1 - trail_pct))
```

顛倒過來會發生什麼：

```python
# 錯誤
if bar_high > peak:          # 先用今天的最高點把停損拉高
    stop = peak * (1 - trail_pct)
if bar_low <= stop:          # 再用拉高後的停損判定今天的最低點
    return exit(...)
```

第二種寫法用**當日盤中最高點**回頭保護**當日的最低點**。但在真實交易裡，最低點發生時你還不知道當天最高會到哪——那是 look-ahead。

這個錯誤不會拋任何例外，只會讓回測變好看。

### 2.3 與 triple-barrier 共通的四條規則

換標記方式不改變這些：

| 規則 | 為什麼 |
|---|---|
| 進場是 **T+1 開盤** | T 日特徵要收盤後才算得出來；三大法人資料也是盤後才公布 |
| 用 high/low 判定，不是 close | 盤中觸及就是觸及 |
| 跳空穿越時以**開盤價**成交 | 不可假設停在停損價。跳空跌破時你拿不到那個價 |
| 無法確定時回 `None` | 可得 K 棒少於 horizon 且未觸停損時，結果取決於還沒發生的交易日 |

### 2.4 標籤語意的差異

```
triple-barrier   三分類（先碰上柵 / 下柵 / 到期）
移動停損         報酬的正負號（+1 報酬 > 0，−1 報酬 ≤ 0）
```

差別不只是類別數。triple-barrier 每筆 +1 的報酬**都一樣**（就是目標價），所以命中率足以算期望值：

```
E[R] = p × target − (1 − p) × stop
```

移動停損每筆的報酬**都不同**（可能 +3%，也可能 +112%）。命中率不足以描述期望值——這直接決定了校準層必須改（第四節）。

### 2.5 實測對比

同一段合成資料（連續 30 天每日 +3% 後回落）：

```
固定目標 triple-barrier :  +22.99%   持有  8 天
移動停損 trailing-stop  : +112.09%   持有 31 天   期間最高 242.7
差距                     :   89.10 個百分點
```

## 三、停損幅度怎麼推導

### 3.1 不能照抄 `barrier_width.derive_width`

固定停損與移動停損的**受測次數**不同：

```
固定停損   進場時設定一次，只有價格跌破才觸發
移動停損   每天隨高點上移，整個持有期都在被測試
```

同樣寬度，移動版被觸發的機率高得多。直接沿用 `atr_multiple = 0.8` 會把部位在趨勢中途掃出場——那就回到「上檔被封死」的老問題。

### 3.2 直接量測「這檔通常回落多少」

```
對每個已走完的 horizon 長度視窗：
    區間最高 = cummax(high)
    回落     = 1 − low / 區間最高
    該視窗的最大回落 = max(回落)

trail_pct = 這些最大回落的第 q 分位數
```

**這個量測方式與標記器的觸發邏輯完全一致**（以 high 累積峰值、以 low 判定），所以分位數的意義是直白的：

> q = 0.80 → 歷史上 80% 的持有期，這個停損不會被觸發

ATR 不足以取代它。ATR 量的是**單日**振幅，移動停損承受的是**多日累積**回落——兩者可以差好幾倍。ATR 仍然計算並記錄，作為稽核依據。

### 3.3 q 是唯一真正的參數

它控制一組對立的代價：

```
q 太小  →  被日常雜訊掃出場，永遠跟不到趨勢
q 太大  →  停損形同虛設，回吐過多獲利
```

實測推導出的幅度（q = 0.80）：

| 持有期 | 平均 trail_pct | 觸停損出場比例 |
|---|---|---|
| 20 日 | 13.41% | 37.2% |
| 40 日 | 18.92% | 34.8% |
| 60 日 | 23.93% | 27.4% |

持有期越長、停損越寬——因為視窗越長，期間內能發生的回落越深。這是機械性的，不是調出來的。

### 3.4 上下限是防呆，不是旋鈕

```
地板 = 一趟來回成本（取自 config/costs.py，禁令 3）
       比交易成本還窄的停損沒有意義——被掃出場的代價大於它保護的金額
天花板 = 30%
       再寬就不是風險控制了
```

綁定時 `floor_applied` / `cap_applied` 會標記，讓報告看得見「這檔的寬度是被夾住的」。

### 3.5 反 look-ahead

回落樣本只取決策日當天或之前**就已經走完**的視窗。

測試 `test_pullback_future_crash_is_invisible` 就是守這條：構造兩份資料，前 20 天完全相同、第 21 天起一份暴跌，決策日設在第 20 天。兩者算出的樣本必須逐項相等。

## 四、校準層：從命中率改成期望報酬

### 4.1 為什麼非改不可

triple-barrier 的校準器回答「這個分數的歷史命中率是多少」。移動停損沒有固定目標，命中率無法換算成期望值——+1 可能是 +3% 也可能是 +112%。

所以 `ReturnCalibrator` 直接校準**每箱的歷史平均實際毛報酬**。

### 4.2 每箱要帶離散度

```
平均 +8%，標準差 40%   →  是賭
平均 +8%，標準差  2%   →  才是邊際優勢
```

只報平均數等於藏起一半的資訊。`ReturnBin` 同時帶 `mean_return`、`return_std`、`n_samples`。

### 4.3 鑑別力用成本當門檻

```
最高箱平均報酬 − 最低箱平均報酬  <  一趟來回成本  →  無鑑別力
```

即使排序方向正確，差距賺不回交易成本就等於沒有鑑別力。用成本當門檻而非拍一個 0.01，是因為這個數字本來就是「值不值得交易」的自然分界。

### 4.4 進場門檻改寫

```
triple-barrier   P(+1) ≥ (stop + cost) / (target + stop)
移動停損         E[毛報酬] − cost > 0
                 且  E[毛報酬] − cost ≥ z × 標準差 / sqrt(樣本數)
```

第二道門檻是對症下藥：前一輪的 OOS 報告已經指出「獨立交易期只有 6~15 個，統計結論極不穩定」。要求**優勢大於一個標準誤**，樣本少、離散大時自動變嚴，樣本多、穩定時自動放寬。

離散度未知（樣本 < 2）時保守拒絕——當成 0 等於假設「這個估計完全沒有誤差」，那是最危險的假設。

### 4.5 沒有 R:R

移動停損沒有目標價，所以沒有風報比可算。

**不得拿「期望報酬 / trail_pct」硬充 R:R**——那是兩個不同的量（期望值 vs 最好情況），混用會讓門檻的意義說不清楚。風險紀律由統計顯著性門檻承擔。

## 五、為什麼必須重寫回測引擎

這是整輪工作裡影響最大的改動。

### 5.1 `engine.py` 結構上只容得下一個持倉

它把各期報酬**依序複合**：

```
週 1 報酬 × 週 2 報酬 × ...
```

要餵重疊持倉進去，複合結果會爆掉（前一輪實測：105 個重疊的 60 日持倉複合成 **+10,618%**）。當時的修法是加一條「前一筆出場後才開新倉」。

那條規則修好了數字，卻默默把策略改成**單槽位**。

### 5.2 後果

```
移動停損 OOS 曝險   23 ~ 39%
等權買進持有曝險    100%
```

在 +305% 的多頭裡，光是「七成時間空手」就足以輸掉，**與選股能力完全無關**。

不修掉它，任何「策略輸給買進持有」的結論都不成立——那是在測回測框架的限制，不是測策略。

### 5.3 `portfolio_sim.py` 的模型

```
槽位     固定 n 個（預設 3，對應 Top 3）
配置     開倉時撥出「當下權益 / n」，受現金餘額限制
出場     到標記給定的出場日，槽位釋放、現金回收
現金     空手期間報酬為 0（不假設有貨幣市場收益）
成本     一趟來回在出場時一次扣除
```

**權益逐日標記市值**——只在出場日跳一次會低估最大回撤，而 MaxDD 正是跟買進持有對比時最關鍵的風險指標。

### 5.4 兩個引擎的職責分工

```
engine.py         單筆交易的品質（報酬、成本、換手率）
portfolio_sim.py  整個組合的表現（權益曲線、曝險、回撤）
```

`engine.py` 保留：它算換手率與成本敏感度的介面已經被 CLAUDE.md 規格 13、15 綁死，而且單筆視角在檢查交易品質時仍然有用。

### 5.5 改動前後

同一批訊號、同一段 OOS：

| | 單槽位（engine） | 3 槽位（portfolio_sim） |
|---|---|---|
| 曝險 | 23 ~ 39% | 73 ~ 87% |
| 跑贏隨機 | 3 / 9 | 8 / 9 |
| 跑贏買進持有 | 1 / 9（有效樣本 1） | 3 / 9 |

## 六、過程中修掉的三個真 bug

三者的共同點：**都不會拋錯，只會讓數字看起來很正常。**

### Bug 1：決策日沒有跨標的對齊

各檔用 `range(WARMUP, len(bars), 5)` 產生決策日，但各檔起始日不同（序列長度 760~892），`bars.index[idx]` 落在**不同日曆日**。

症狀：

```
同一決策日的候選數 = [1, 2, 36, 35, 1, 3, 35, 1, 6]
```

候選只有 1 檔時，「挑 Top 3」等於沒有挑。60 日組的三個決策日候選都是 1 檔，**與隨機對照 100% 重疊**，卻顯示「跑贏買進持有」。

修法：決策日取自**共用交易日曆**，每檔用日期查自己的位置索引。

### Bug 2：fold 切分重複扣了暖機期

```python
first_train = (WARMUP_DAYS + FIRST_TRAIN_DAYS) // DECISION_STRIDE   # = 150
```

但決策日本身已經排除暖機期，可用的決策日只有約 128 個。`cursor` 從一開始就超出範圍，while 迴圈一次都沒跑。

修 Bug 1 之後才浮現——之前碎片化的日期數（每檔貢獻自己的日期）把它掩蓋了。

### Bug 3：年化用錯期數

```python
periods_per_year = 252 / horizon      # 20 日 → 12.6
```

持倉不連續時這個換算不成立。實測：9 期實際跨了 **1.10 年**，但公式假設 9 / 12.6 = **0.71 年**，把 +286% 年化成 **+564%**。

修法：用實際經過的日曆時間。

## 八、結論摘要

| 問題 | 答案 |
|---|---|
| 「目標價封死上檔」的解釋對嗎？ | **對。** 移動停損每筆贏同期等權 +2.75 ~ +15.21 個百分點 |
| 移動停損能跑贏買進持有嗎？ | **不穩。** 2~3 槽贏、5~8 槽輸。槽位數不是策略參數 |
