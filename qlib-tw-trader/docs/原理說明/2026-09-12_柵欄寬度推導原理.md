## 問題：目標價與停損價不可以「拍一個數字」

Triple-barrier 需要兩個參數：`target_pct`（目標幅度）與 `stop_pct`（停損幅度）。

直覺做法是拍定值，例如「停損 5%、目標 10%」。這有兩個問題：

### 1. 忽略波動度差異

```
台積電     日均振幅約 2%   →  5% 停損 ≈ 2.5 天的正常波動
某中型股   日均振幅約 6%   →  5% 停損 ≈ 不到 1 天的正常波動
```

同一個 5% 停損，對低波動股是合理的風控，對高波動股是**被日常雜訊掃出場**。

### 2. 忽略歷史報酬分布

若某檔股票近一年的 5 日報酬中位數是 1%，設 10% 目標等於要求一個歷史上很少出現的事件。目標永遠碰不到，標籤全部落在「時間柵到期」或「觸停損」。

### ChatGPT 來源的原話

（見 `docs/需求規劃/202609/來源原文/02_ChatGPT_台股量化軟體比較.md`）

> 不要人工設定 `Buy = Current Price × 0.96`，而是讓模型研究
> 「歷史上這種型態，什麼價格位置進場最有效？」

`CLAUDE.md` 據此明文規定：

> `target_pct` / `stop_pct` **不可人工寫死**，須由 ATR 分位數與歷史相似型態報酬分布推導

## 解法一：停損由 ATR 決定

```
stop_pct = atr_multiple × ATR(n) / close
```

ATR（Average True Range）是波動度的標準度量。用它決定停損距離的意義是：

> 停損要設在「日常波動之外」，而不是一個固定百分比。

### True Range 必須含跳空項

```
TR = max( high − low,
          |high − prev_close|,
          |low  − prev_close| )
```

**為什麼三項都要**：

```
D1  收盤 100
D2  high 105、low 104   （整根在前收之上，跳空開高）

只用 high − low     → TR = 1      嚴重低估
含跳空項            → TR = max(1, |105−100|, |104−100|) = 5
```

跳空是真實的價格移動，忽略它會系統性低估波動度，進而設出過窄的停損。

測試：`test_atr_accounts_for_gaps`

### 視窗不足必為 NaN

```python
true_range.rolling(window=period, min_periods=period).mean()
```

`min_periods=period` 確保前 N 筆是 NaN，不用不完整視窗硬算。

第一筆另外要手動設 NaN——它沒有前收盤價，True Range 本身無定義。

### 地板與天花板

```python
stop_pct = min(max(raw_stop, min_stop_pct), max_stop_pct)
```

極端情況需要夾限：

| 情境 | 原始計算 | 夾限後 |
|---|---|---|
| 完全平盤（ATR ≈ 0.02） | 1.5 × 0.02 / 100 = 0.03% | 1.5%（地板） |
| 極端波動（ATR = 40） | 1.5 × 40 / 100 = 60% | 10%（天花板） |

0.03% 的停損會被瞬間掃掉；60% 的停損等於沒有停損。

測試：`test_stop_pct_respects_floor_and_cap`

## 解法二：目標由歷史報酬分位數決定

```
target_pct = quantile( 過去已實現的 horizon 日報酬, q )
```

意義：

> 目標價設在「歷史上這檔股票 horizon 天內達得到的報酬」的第 q 百分位。

`q = 0.85` 表示「歷史上約 15% 的 5 日區間能達到這個報酬」。

### 反 look-ahead：只用已實現的報酬

這裡最容易出錯。

```python
def _past_horizon_returns(close, decision_idx, horizon, lookback):
    last_start = decision_idx - horizon      # ← 關鍵
    ...
```

第 i 天的 horizon 報酬 = `close[i + horizon] / close[i] − 1`。

**只有 `i + horizon <= decision_idx` 時這個報酬才是已實現的。**

若寫成 `last_start = decision_idx`，就會用到 `close[decision_idx + horizon]`——決策日之後的價格 → look-ahead。

測試 `test_target_uses_only_past_returns` 把這條釘死：

```
構造：前 70 天平盤（5 日報酬 ≈ 0），第 70 天後每天漲 10%
在 decision_idx = 69 推導時：
    正確實作 → target ≈ 0（被地板拉到 2%）
    洩漏實作 → target 反映後面的暴漲
```

## R:R 門檻：不足就放棄，不硬湊

```python
if width.risk_reward < min_risk_reward:
    return None
```

**絕不可為了通過門檻而拉高目標價。**那等於用一個不現實的目標價換一個好看的風報比——帳面上 R:R 達標，實際上目標永遠碰不到。

這條的實測價值在下一節。

## 實測：D7 原始參數內部矛盾

原 D7 規格：`horizon=5、atr_multiple=1.5、target_quantile=0.70、min_risk_reward=2.0`

在 0050 前 10 大、2023-01 ~ 2026-09、共 **8,919 個決策日**上實測：

```
覆蓋率      0.38%（34 / 8919）
類別分布    +1 = 0     0 = 28     −1 = 6
```

**`+1` 類別完全為空。**

### 為什麼矛盾

```
ATR × 1.5 導出的停損  ≈ 3%
R:R ≥ 2 要求的目標    ≈ 6~7%
5 個交易日內觸及 7%   → 機率極低
```

三個要求（5 日 horizon、R:R ≥ 2、ATR×1.5 停損）**無法同時成立**。

更糟的是：唯一通過 R:R 門檻的 34 個決策日，是那些「歷史報酬分位數異常高」的時點（剛經歷大漲），而那些時點的 7% 目標同樣不可能在 5 天內達到。

### 修訂方式

**不動 R:R ≥ 2.0**（那是風險紀律，來自 Kimi 的意見），改掉原本拍定的兩個參數：

| 參數 | 原值 | 修訂值 | 理由 |
|---|---|---|---|
| `horizon` | 5 | 5（不變） | 使用者需求就是「未來 5 個交易日」 |
| `min_risk_reward` | 2.0 | 2.0（不變） | 風險紀律，不為湊樣本放寬 |
| `atr_multiple` | 1.5 | **0.8** | 1.5 倍太寬，逼得目標必須拉到不可觸及 |
| `target_quantile` | 0.70 | **0.85** | 0.70 導出的目標太小，過不了 R:R 門檻 |

修訂後（同一資料集）：

```
覆蓋率      55.5%（4,946 / 8,919）
類別分布    +1 = 951    0 = 1,404    −1 = 2,591
平均目標    6.20%       平均停損 2.38%       R:R 2.605
```

三類都有 900+ 樣本，可訓練。

## 參數可行性診斷（不是效能最佳化）

`scripts/diagnose_barrier_params.py` 掃 54 組參數，但**只看標籤分布，完全不看報酬**。

三個判準：

| 判準 | 門檻 | 為什麼 |
|---|---|---|
| 覆蓋率 | ≥ 10% | 太低 → 樣本不足 |
| 每類樣本數 | ≥ 30 | 某類為 0 → 模型退化成常數預測 |
| 到期占比 | ≤ 85% | 過高 → 柵欄相對 horizon 太寬，標籤幾乎不帶資訊 |

**為什麼這不算多重測試作弊**：這個網格不碰報酬，不可能「掃出一組賺錢的參數」。它回答的是純粹的工程問題：「這組參數能不能產出可用的訓練集？」

文件與程式都明文警告：選定參數後的策略績效仍須走完整 Walk-Forward + OOS + PBO 校正。

## 最重要的發現：無條件期望值是負的

修訂後參數的實測統計：

```
R:R                  2.605
基礎勝率（排除到期）   26.85%   （951 / 3,542）
損益兩平勝率          27.74%
勝率缺口              −0.89 個百分點
```

### 損益兩平勝率的推導

不含成本時，期望值為 0 的條件：

```
p × target − (1 − p) × stop = 0
p = stop / (target + stop) = 0.0238 / (0.0620 + 0.0238) = 27.74%
```

實際基礎勝率 26.85% < 27.74% → **無條件期望毛報酬為負**：

```
0.2685 × 6.20% − 0.7315 × 2.38% = 1.665% − 1.741% = −0.076%
```

### 含成本後的門檻

```
p × target − (1 − p) × stop − cost = 0
p = (stop + cost) / (target + stop)
  = (0.0238 + 0.01071) / (0.0620 + 0.0238)
  = 0.03451 / 0.0858
  = 40.22%
```

**模型必須把勝率從 26.85% 提升到 40.22% 以上才有正期望。**

### 這條為什麼比原本的 `P(+1) ≥ 0.55` 有意義

原本 `CLAUDE.md` 寫的 0.55 是拍的。40.22% 是從**實際柵欄寬度與實際成本**算出來的，而且會隨每檔標的的波動度與流動性分層動態變化。

已改為動態門檻：

```
P(+1) ≥ (stop_pct + round_trip_cost) / (target_pct + stop_pct)
```

### 新紅線

> 若 Walk-Forward 的 OOS 勝率無法穩定站上 40.22%，這個策略族就是沒有優勢，如實寫進報告，不進 Top 3。

## NaN 靜默通過門檻：一個真 bug

煙霧測試發現 2317（鴻海）的平均目標是 `nan%`，**而它通過了 R:R ≥ 2.0 的門檻**。

### 根因鏈

```
2317 在 2025-07-30 有一列 OHLC 全為 NULL（上游資料洞）
    ↓
np.quantile(含 NaN 的樣本) → NaN
    ↓
target_pct = NaN
    ↓
risk_reward = NaN / 0.0238 = NaN
    ↓
if NaN < 2.0:  →  False
    ↓
門檻靜默放行
```

### 教訓

> **NaN 不會讓比較拋錯，它會讓比較「看起來通過」。**

`NaN < x`、`NaN > x`、`NaN == x` 全部回 `False`，不會有任何警告。任何門檻檢查前都必須先排除非有限值。

### 修正

兩層防護：

```python
# barrier_width.py：門檻比較前明確排除
if not np.isfinite(samples).all():
    return None
if not (np.isfinite(target_pct) and np.isfinite(stop_pct)) or target_pct <= 0:
    return None
```

```python
# loader.py：資料層預設剔除缺漏列，並揭露剔除了什麼
load_prices(..., drop_incomplete=True)
price_quality_report(...)   # 不靜默丟棄
```

全標的池掃描結果：**11 檔有資料洞，共 12 列**

```
1101 [2025-08-13]   1102 [2024-06-05]   1504 [2025-07-30]
2207 [2025-12-18]   2317 [2025-07-30]   2449 [2024-04-26]
2884 [2025-11-05]   2887 [2024-08-22]   3036 [2023-09-14, 2025-07-15]
7750 [2024-06-18]   7769 [2024-11-01]
```

測試：`test_nan_in_close_must_not_pass_risk_reward_gate`

## 可稽核性

`BarrierWidth` 帶出完整推導依據：

```python
atr_value        當時的 ATR
atr_period       用的視窗
atr_multiple     乘數
target_quantile  分位數
lookback         回看期數
sample_size      實際樣本數
```

`CLAUDE.md` 禁令 7、8 要求可稽核。沒有這些欄位就無法回答「為什麼 2026-09-12 的台積電停損設在 2.38%」。
