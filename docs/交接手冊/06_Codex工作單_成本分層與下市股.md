## 任務 J：成本分層拿還原價當成交價（先做這個）

### 問題

`config/costs.resolve_tier(price, amount, is_etf)` 用 `price` 判斷
「這一檔買不買得起整張」：

```python
whole = amount >= price * LOT_SIZE      # LOT_SIZE = 1000
```

N=10 時 `amount = 40,000`，所以門檻是**股價 40 元**。

但回測傳進去的是**還原價**。`loader.load_prices(adjusted=True)` 會用
`adj_close` 覆寫 `close` 並以同比例調整 OHL，所以下游拿不到實際價。

### 量到的幅度

還原價 / 實際價（全庫、每年 6 月）：

```
年度    平均比值   最低      40 元門檻分層不同的比例
2016    0.8666   0.0000    13.41%
2018    0.8829   0.0442
2020    0.8715   0.0000    10.89%
2022    0.8812   0.0653
2024    0.9259   0.0000     3.46%
2026    0.9773   0.0000
```

**還原是回溯調整、錨在最新日，所以越早的日期還原價越低。**
開發集（2015~2023）正是落差最大的那一段。

### 方向對策略有利

```
還原價偏低  →  看起來買得起整張  →  走 0050-lot（0.671%）
實際價較高  →  其實只能買零股    →  應走 0050（1.071%）
```

**成本被低估 0.4 pp/趟。** 這與第 14 個 bug（拿 N=3 的部位大小論證
N=10 的成本）是同一類：錯的方向一律是讓結果變好看。

決策日當天沒有這個問題（實測 10 檔落差全部 0.0%），所以**前推帳本
不受影響**，要修的是回測。

### 做什麼

1. 讓 `resolve_tier` 的可負擔性判斷拿到**實際收盤價**，報酬計算繼續用
   還原價（禁令 12）。

   設計自己決定，但必須滿足：
   - 不可在腳本裡自己查 `stock_daily`——那會繞過 loader 的凍結守門
   - 不可把兩種價格混在同一個欄位靠命名區分
   - 缺實際價時**拋錯或明確標記，不可靜默退回還原價**

2. 開發集重跑檔數掃描（N = 1/3/5/10/15/20），與現有那張表並列：

   ```
     N    每檔金額     毛/趟   實際成本    淨/趟   年化淨  整股比例  逐年正
    10    40,000    4.89%   0.913%   3.98%   27.9%   39.4%   7/8
   ```

   來源：`qlib-tw-trader/docs/原理說明/2026-09-16_ETF納入與逐檔成本更正.md`

### 驗收

```
□ 整股比例下降（N=10 的 39.4% 應該變小；若沒變，說明為什麼）
□ 新舊兩張表並列，逐欄差異寫出來
□ 不重跑 2024 年以後的任何區間（禁令 6）
□ 測試比對手算值：給定實際價 42 元、還原價 38 元、amount 40,000
  → 必須判為零股
□ 全套測試通過（目前 757 passed）
```

⚠️ **不要順手把 OOS 的數字更新掉。** 那份報告對應的是當時的程式，
改了成本模型要出新報告、註明區間已用掉，不可就地改寫歷史結論（禁令 9）。

## 任務 K：下市股的處理從來沒驗過（禁令 2）

### 現況

```
stock_master 標記下市                    159 檔
其中曾進過 market_cap 標的池              19 檔
其中因 MIN_SERIES_LENGTH=400 被剔除        4 檔（2833 2847 4733 6286）
```

被剔除的 4 檔都在 2015~2016 下市，**影響開發集，不影響 OOS**。

### 真正的問題不是長度過濾，是靜默剔除

`validate_oos_momentum.py`：

```python
forward = closes.shift(-HOLDING_DAYS) / opens.shift(-1) - 1
...
realized = forward.loc[day].dropna()
common = ranked.index.intersection(realized.index)
```

**一檔股票在持有期內停止交易 → `shift(-40)` 是 NaN → `dropna()` 把它
從候選集裡整個拿掉。** 它不是「被持有到下市然後記一個真實結果」，
而是「當天根本不存在」。

### 具體重現

```
2888 新光金
  2025-07-01 快照   market_cap 排名 53      ← 合法候選，排名很前面
  2025-07-11        最後交易日
  2025-07-24        下市

2809 京城銀
  2025-07-01 快照   market_cap 排名 135
  2025-09-17        最後交易日
  2025-10-01        下市
```

2025-07-01 到 2025-07-11 之間的任何決策日，2888 都是市值前 60 名的
合法候選，但它會被 `dropna()` 無聲移除。

### 方向不明，所以必須量

曾進池的 19 檔下市股裡，2024 年之後的三檔**全部是金融保險**：

```
代號    名稱     產業      下市日       最後有價日
2888  新光金   金融保險   2025-07-24   2025-07-11
2809  京城銀   金融保險   2025-10-01   2025-09-17
2867  三商壽   金融保險   2026-09-01   2026-08-19
```

大型金控的下市通常是併購／換股而非財務危機，**如果是這樣**，剔除它們
會是低估報酬——與一般的倖存者偏差方向相反。

⚠️ **這只是假設，資料庫裡沒有下市原因欄位。** 請自己查證每一檔的實際
下市原因再下結論，不要沿用我這個推測。方向弄反了整個結論就反了。

### 做什麼

1. 寫一份診斷，列出開發集上**每一筆**因缺未來價而被 `dropna()` 移除的
   `(決策日, 代號, 當時排名, 當時分數)`，並標記是否為已知下市股。

   關鍵：要區分兩種缺值
   - **下市**：`stock_master.delisted_date` 有值，永久停止交易
   - **停牌／缺資料**：之後又有價格

   兩者處理方式不該相同。

2. 對下市股實作一個**明確的**政策，並在開發集上量它的影響。
   至少並列兩種：

   ```
   政策 A  維持現狀（靜默剔除）              當基準線
   政策 B  持有到最後有價日，用那天收盤結算    再投入現金至到期
   ```

   政策 B 的實作細節你決定，但**不可回填前一日價格假裝有成交**
   （`record_forward.py` 的結算已經有這個紀律，照抄）。

3. `MIN_SERIES_LENGTH = 400` 剔除的 4 檔要單獨報告：它們進池幾次、
   在哪些決策日本來會是候選、剔除它們改變了什麼。

### 驗收

```
□ 逐筆清單（決策日 / 代號 / 排名 / 分數 / 下市或停牌）
□ 政策 A vs B 的開發集對照：毛/趟、淨/趟、逐年為正、樣本數
□ 明確回答：剔除下市股是高估還是低估報酬，幅度多少
□ 若影響 < 0.1 pp/趟，如實寫「量到了，很小」——不要為了有結論而放大
□ 測試：合成一檔在持有期第 20 日停止交易的股票，驗證政策 B 的報酬
  等於手算值
□ 不重跑 2024 年以後的任何區間
```

⚠️ **這件事可能會否定已經跑掉的那次 OOS。** 那次 OOS 載入到
2026-09-11，而 2888（2025-07-24）與 2809（2025-10-01）都在區間內下市，
2867（2026-09-01）落在最末端。

如果政策 B 在開發集上造成顯著差異，那份 OOS 報告必須加註
「此結果採用政策 A」——**不是重跑，是加註**。

## 任務 L：defensive 約束目前提供零保護（可選）

### 問題

CLAUDE.md 投組約束第三條「至少 1 支 defensive（低 beta）」，
實測效果與無約束**完全相同**（不是差異小，是一模一樣）：

```
baseline 前 10 檔裡 beta < 1.0 的檔數
  中位 8 檔   最少 2 檔   最多 10 檔   等於 0 的期數 0/36
```

原因：beta 的基準是 0050，而 0050 由台積電主導、本身就是高 beta。
拿它當分母，150 檔大型股裡大多數 beta 自然 < 1.0，
`DEFENSIVE_BETA_MAX = 1.0` 篩不掉任何東西。

### 做什麼

至少試一個方向並量結果：

| 方向 | 備註 |
|---|---|
| 用標的池自己造市值加權指數當基準 | 價格與市值資料都有，不需外部資料 |
| 改用 beta 的橫斷面分位（如最低 30%） | 這是**改規格**，要先寫依據 |
| 回到原文的「高股息」 | `stock_daily_per` 殖利率覆蓋率僅 4.3%，大概不可行 |

### 驗收

```
□ 修完之後這條約束在 36 期裡綁到幾期（現在是 0）
□ 對淨/趟的配對差異與標準誤（見下面「怎麼報數字」）
□ 若結論是「這條約束在 N=10 沒有意義」，那也是合格的結論——
  寫清楚就好，不要硬湊一個會綁到的定義
```

## 怎麼報數字（三張工作單累積下來的規矩）

### 1. 點估計不算結論，要配對標準誤

主線量投組約束的代價時，彙總表看起來很明確：

```
全部嚴格   淨/趟 3.28% → 1.52%      年化 22.5% → 10.0%
```

配對之後：

```
差異 −1.75 pp   標準誤 1.58 pp   t = −1.11   量不出差別
```

**36 期、優勢集中在 1.7~4.3 檔名字上，所以 2 SE = 3.16 pp，而優勢本身
只有 3.28 pp。** 這種檢定只能偵測「整個優勢被消滅」。

所以報告一律寫「無法排除 X 的代價」，不要寫「沒有影響」。
配對相減的理由：同一批決策日、同一份候選池，未配對的標準誤裡含著
「這一期市場好不好」的共同變異。

做法可參考 `scripts/diagnose_constraints.py` 的 `paired_report()`。

### 2. PBO / DSR 的輸入很容易餵錯

主線餵錯過兩次：

```
錯   CPCV 的 15 條路徑總報酬當成時間序列   ← 那不是序列
錯   2,196 筆重疊的日報酬當觀察數          ← DSR 讀成 1.0000
對   有效樣本數 = 天數 ÷ 持有期            ← 36 期，DSR 0.9741
```

`n_observations` 要用**有效**樣本數，且需 ≥ 30。

### 3. 掃了幾組就要說幾組

DSR 的懲罰隨候選數變化。主線掃 126 組（3 族 × 7 持有期 × 6 檔數）時
DSR 是 0.0042，不通過。**掃了就要報，不可只報最好那一組。**

### 4. 不要用 `pd.offsets.BDay` 算到期日

低估台股假日。實測持有期 60 日時差 5 天、最壞 14 天。
一律用 `data/calendar.due_trading_date()`。

## 順序與範圍

```
J  先做   影響所有成本數字，是其他量測的地基
K  再做   可能改變 OOS 結論，但要先有正確的成本模型
```
